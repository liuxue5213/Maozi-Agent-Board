# 屏幕色彩对照

配置文件：[color-map.json](../client/workbuddy/web_assets/color-map.json)。

**屏幕不是 RGB888 直出。** 面板是 ST7796（竖屏 320×480、RGB565），每个通道先被
截到 5/6/5 位才上屏，所以 Web 里的 `#RRGGBB` 只是「请求色」，不等于屏幕最终显示的
颜色。深色主题里这个偏移肉眼可辨——实机参考主题的底色 `060B16` 上屏后是 `000810`
（R、B 各偏 6）。因此**任何要显示在屏幕上的颜色都必须先过映射**，`hex` 不能直接
当成品色用。

生成与校验：`python3 client/tools/gen_color_map.py`（`--check` 只校验不写盘）。
`hex` 是唯一来源，`rgb565` 与 `flushWord` 都由它按面板位宽推导，手改 hex 后跑一次
就不会漂。换屏或换控制器时改 `panel.pixelFormat` / `panel.calibration`，再跑生成器。

## 实机校准

- 面板为 ST7796，竖屏 320×480，渲染格式 RGB565。
- 2026-10-10 的 24 格实机测试中，用户选择 **第 7 格**，第 5 格观感偏深。第 7 格使用 RGB 通道顺序、`cfg.invert = true`，并在 `flush_cb` 中交换每个 RGB565 像素的两个字节。
- 红、绿、蓝、白原色与后续深蓝灰主题已通过照片核对。色卡中的其他颜色是数学换算值，未逐一用仪器测量。屏幕背光、相机白平衡和面板批次都会影响实际观感。

## 三个数值的关系

```
请求 sRGB888 ──截位──► RGB565 字 ──换字节──► flush 字 ──上屏──► 观感
     hex            rgb565        flushWord
```

`flushWord` 是驱动层的字节序细节，**不会改变最终观感**——它存在的意义是让颜色
在正确的通道上落地。所以预览要复现的是「截位后的颜色」，字节交换只作为标定信息
展示；Web 端**不要**自己换字节。

## 字段含义

| 字段 | 含义 |
| --- | --- |
| `hex` | 请求的 sRGB888，六位 `RRGGBB`。**这是唯一来源。** |
| `rgb565` | `hex` 按 R5/G6/B5 截位后的 16 位数值。 |
| `flushWord` | `rgb565` 交换高低字节的数值，对应第 7 格校准代码。 |
| `panel.calibration` | 实机测定的通道序 / 是否换字节 / 是否硬件反相。**驱动层参数，不能靠改 JSON 修通道错误。** |
| `themeBindings` | 七个可由 Web 改动并经 CFG 同步的主题槽位。 |
| `semantic` | 固件写死或已用于状态/装饰的颜色。`editable: false` 表示 Web 改不了。 |
| `checks` | 黑白与原色、混合色的校准样本。 |
| `palette` | 21 级中性灰和 12 个色相、每色相 19 级明度，共 249 个候选色。 |
| `diagnosticVariants` | 24 格测试中每格的通道顺序、换字节和软件反相参数。 |
| `referenceTheme` | 用户确认过的实机主题，作为回归基线。 |

`status.ok/warn/err`、`robot.*`、`saver.*` 标记为 `editable: false`：它们写在固件
里，Web 改不了，但**预览必须照抄**——否则「预览好看、实机不一样」会再次出现。
将来若要实时修改状态色，需要同时扩展 CFG schema、固件 profile 和渲染器。

## Web 端如何使用这份映射

1. **预览同源。** 任务视图与息屏显示的画面不是另画的效果图，而是按
   `firmware/src/ui.cpp` 的 320×480 坐标、字号映射逐项复刻；颜色一律先过
   `panelColor()`（截位 → 还原 → 按 `panel.calibration` 处理通道序）。七个主题色
   走 CSS 令牌 `--dev-*`，固件写死的色走 `devSemantic(id)` 从本文件读取。
2. **色卡显示上屏色。** 「设置 → 主题配色 → 屏幕色彩对照」里每张色块的填充是
   **屏幕会显示的颜色**；有量化偏移时右下角小方块是请求色。每张卡的标题（鼠标悬停）
   给出 `请求色 → 屏幕色`、`RGB565`、`flush` 与最大通道偏移。
3. **取色器旁有偏移提示。** 七个主题色取色器下方那行会报出当前最大的量化偏移
   （例如「背景 Δ6（#060B16 → #000810）」），超过 Δ8 转警告态；选完色就能看见，
   不必等上屏才发现偏色。
4. **校验按上屏值算。** `profile.validate_profile` 的文字/卡片对比度门槛一律用
   量化后的颜色核算：请求色过 AA、量化后不过的组合会被拒绝。校验结果里的
   `theme.panel` 字段给出七色的上屏值，便于诊断包与导出配置核对。
5. **卡片要按「合成后」的颜色算。** 卡片是半透明的：固件 `box()` 用
   `bg_opa = card_opa` 把 `card` 叠在渐变背景上，所以屏幕上真正的填充色是
   **合成结果**，不是 `card` 本身。不透明度越低，填充越贴近背景、边界越看不清。
   校验因此对渐变的**两端（bg / grad）分别合成**并取最差：屏幕是 bg→grad 的竖向
   渐变，卡片下沿压在更亮的 grad 上，那里的边界最弱。`theme.panel_fill` 就是
   这个合成填充色，可用于核对。

   实测意义：只按 `card` 原色校验会系统性高估可辨识度——15 套已发布主题里有
   11 套的实际边界低于 1.5:1（例如 山峦黄昏 65% 不透明度下只有 1.18:1）。
   所以主题预设现在**各自带 `card_opa`**，色板点击不再沿用用户当前的透明度，
   否则同一套预设「在 100% 时能存、在 70% 时报边界看不见」。

   调参方向：不透明度越低，`card` 就要越亮（提亮 `card` 优于直接拉满不透明度，
   这样背景图仍能透出来）。`tests/test_theme_presets.py` 会把界面上能点的每套
   主题都跑一遍校验，改配色时它先拦。

任意六位 RGB 色仍可通过 Web 颜色输入框设置；色卡不是允许使用的颜色上限。
若更换屏幕或控制器，应先用诊断矩阵重新测定 `PANEL_COLOR_ORDER_BGR`、
`PANEL_COLOR_BYTESWAP` 与 `cfg.invert`，再更新本文件的 `panel.calibration`；
不能只修改 JSON 来修复驱动层通道错误。

固件侧的位宽是 `firmware/src/config.h` 的三个宏，Web/Python 侧是
`color-map.json` 的 `panel.pixelFormat` 与 `client/workbuddy/profile.py` 的
`PANEL_BITS`——三处必须一致，`tests/test_panel_color.py` 会拦住漂移。
