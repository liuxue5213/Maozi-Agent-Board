# 宠物包资产管线 v1（P1-4 收口）

> 起草：2026-10-15 · 关联：P1-2 宠物双路径收口（`pet_render.render_model` 单一事实源）· R6 资产管线未定义
> 仓库身份：`github.com/liuxue5213/Maozi-Agent-Board`（main / origin/main）

## 0. 目标

把「JPEG 宠物包」从散落的 `outputs/petpack_*/`（未跟踪、无元数据）收口为**有策略、可审计、带完整性校验**的资产管线，明确四件事：

1. **进仓库策略**：源 JPEG 进不进 git？manifest 进不进？
2. **传输校验**：下发到设备前/中如何保证不传坏图？
3. **PSRAM 上限**：皮肤包占用多少设备内存，何时该拦？
4. **缺帧回退**：包不完整时设备怎么表现？（已在 P1-2 落地，此处确权）

## 1. 资产模型（与 P1-2 对齐）

| 路线 | 载体 | 进固件？ | PSRAM | 角色 |
|---|---|---|---|---|
| **canonical 内置矢量** | 程序化 `draw_pet`（9 态） | 是（出厂） | 0 | 默认 + 回落终点 |
| **可选皮肤 JPEG 包** | `pet_<状态>.jpg`（LittleFS） | 否 | 按帧占用 | 用户按昼/夜/雨雪选择 |

设备端规则不变：**有 `pet_<状态>.jpg` 即渲染图片，无则回落矢量**。`pet_render.render_model` 是「当前到底渲染哪条路线」的客户端唯一事实源。

## 2. 进仓库策略（结论）

- **`outputs/petpack_*/pet_*.jpg` → 不入库**（`.gitignore`）。理由：源图可由 `tools/pet_artwork.py` 确定性再生成（`--pack <名> --scene <场景> --palette <毛色>`），进库只会膨胀体积且易与生成器漂移。
- **`outputs/petpack_*/manifest.json` → 入库**（审计载体）。它不含二进制，纯元数据（CRC32 / 尺寸 / 预算），是「这个包此时此刻是什么」的权威描述。
- **导入端点**（`/api/petpack-import`）收到 `.zip` 后写帧 + 立即写 manifest；**生成器**写完帧后立即写 manifest；**现有 12 个包**已回填 manifest。

> ⚠️ **存量包的历史包袱**：P0-1 期间 136 个 `pet_*.jpg` 已被提交跟踪，`.gitignore` 对**已跟踪文件无效**。其中 `xingli/xuebai_v2` 等的互动帧（`feeding/drinking/playing` + B 变体）**非 `pet_artwork.py` 生成器产物**（生成器只产 9 帧），属手工/外部精修资产——若 `git rm --cached` 回溯取消跟踪会丢失这些独特帧且无法再生。故**保留存量跟踪现状**，`.gitignore` 仅对未来新生成的 jpg 生效（防止 `git add outputs/` 误带）；若后续要把存量包彻底收敛为「生成器可再生产」，须先补齐生成器对互动帧的支持，再统一取消跟踪。

> 若某包要「固化为出厂预设皮肤」，单独走打包流程（P1-3），不走散落 `outputs/`。

## 3. Manifest 结构

`manifest.json`（由 `pet_render.build_pack_manifest` 统一产出，客户端/生成器共用）：

```jsonc
{
  "name": "shiba",
  "states": ["working", "working_b", ...],     // 实际存在的帧
  "missing": [],                                 // 缺的规范帧
  "fallback": {"working_b": "working"},          // 缺帧回退目标
  "frames": [                                    // per-frame 明细（审计核心）
    {"state": "idle", "file": "pet_idle.jpg",
     "size_bytes": 16007, "crc32": "AE3AD251", "decoded_kb": 300}
  ],
  "total_decoded_kb": 2700,                      // 所有帧解码后总占用
  "source_cap_kb": 100,                          // 单帧源 JPEG 硬上限
  "over_source_cap": [],                          // 超源上限的帧（空=OK）
  "psram_budget_kb": 3600,                        // 12 槽 × 300KB 最坏驻留
  "within_budget": true,                          // total_decoded_kb <= 预算
  "cache_pressure": false,                        // frames > 12 槽
  "generated": "2026-10-15T14:02:00Z"
}
```

## 4. 传输校验（两层）

| 层 | 位置 | 校验 | 抓什么 |
|---|---|---|---|
| **线路层** | `app.send_bg_image` → `IMG=BEGIN,len,crc` + 设备侧 CRC 回包 | CRC32 每帧 | 传输比特错误 / 解码超时 |
| **预检层（P1-4 新增）** | `web.petpack_integrity_check` → `app._preflight_petpack` | 磁盘帧 CRC32 与 **manifest 记录**比对 + 单帧源上限 | **源文件已坏 / 部分下载 / 被改**；单帧源 > 100KB |

预检在「清空当前皮肤（删 `pet_custom`）」**之前**执行——坏包不会先误删在用的形象。预检失败直接返回 `preflight` 原因，整包不上传。

> 线路层 CRC 只能保证「传过去的和传之前一样」；预检层保证「传之前磁盘上的图和当初生成/导入时一致」。两层互补。

## 5. PSRAM 上限（口径）

- 单帧解码 = 320×480×2 字节（RGB565）= **300 KB**。
- 设备 `bgimg.cpp` anim_cache = **12 槽** → 最坏驻留 **3600 KB**（`PET_SKIN_PSRAM_BUDGET_KB`）。
- **硬阻塞条件**：任一帧**源 JPEG > 100 KB**（固件 `MAX_IMG` 解码行缓冲上限）→ 预检拒绝，避免设备解码崩。
- **软提示条件**：皮肤帧数 > 12（`cache_pressure`）或 `total_decoded_kb > 3600`（`within_budget=False`）→ Web 库标「缓存压力」，**不阻塞上传**——因为设备用 LRU 只保留最近 12 帧解码驻留，其余留 LittleFS 按需解码。

> 现有 `shiba(15)` / `xingli(20)` / `xuebai_v2(20)` 三包越过 12 槽预算，显示缓存压力提示但可正常下发（LRU 兜底）。若要彻底消除压力，把它们的互动/双帧（互动帧 `feeding/drinking/playing` + B 帧）改为「矢量/基础帧兜底」或精简到 ≤12 帧——待产品决策。

## 6. 缺帧回退（确权）

- 规范 9 态缺任意 → 该状态不更新图片，停在上一帧/基础帧；整包回落矢量以「完整优先」。
- `working_b` 缺 → 回退 `working`（无交替动画，仅 A 帧常显）；其余规范帧缺 → 回退 `idle`。
- `render_model` 中 `fallback_to_builtin=True` 时 Web 摘要告警并切回内置矢量。
