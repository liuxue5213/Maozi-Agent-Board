## 1. 核心功能与技术架构

### 1.1 双层架构

| 层 | 技术选型 | 职责 |
|---|---|---|
| 电脑端 | Python 3，纯标准库 + `psutil` + `pyserial`（仅 2 个第三方依赖） | 指标采集、AI 任务识别、配置编辑与校验、配置下发、动作执行、本机 Web 设置页 |
| 设备端 | ESP32-S3（16MB Flash / PSRAM n16r8）+ LVGL 8.3.11 + LovyanGFX + ArduinoJson | 渲染 320×480 竖屏、触控导航、DHT11 温湿度、配置持久化、闹钟 |
| 链路 | USB 虚拟串口 115200，文本 `KEY=VALUE` + 二进制分帧（未实现） | 遥测 1Hz、心跳 5s、配置事务 |

### 1.3 配置同步契约（项目最成熟的部分）

```
客户端 validate_profile()  ← 纯 Python 规则，含 WCAG 4.5:1 对比度与 gb2312 字库覆盖检查
   ↓ base64 每片 ≤90 原始字节
CFG=BEGIN,<ver>,<len>,<CRC32>
CFG=DATA,<ver>,<seq>,<b64>
CFG=END,<ver>
   ↓ 固件校验 len → CRC32 → schema → 组件支持 → 布局合法性
LittleFS 写非活动槽（按 version 奇偶选择 a/b）
   ↓
ACK=CFG,<ver>,APPLIED   /   NAK=CFG,<ver>,<REASON>
```

**评价：这套设计质量高。** 三处值得肯定：

1. **失败不破坏上一有效配置**：`decode_profile` 先在 `new` 出的候选对象上完整校验，通过才 `g_profile = *candidate`；写入用 `remove(dest)` + `rename(tmp,dest)`，掉电只会丢当前槽，另一槽仍保留旧版本。`profile_init` 加载两槽取 `version` 较大者。
2. **拒绝原因可枚举**：`SIZE / SEQ / DATA / LENGTH / CRC_MISMATCH / MEMORY / INVALID_CONFIG / STORAGE` 直接进 `NAK`，客户端 `parse_uplink` 能解析出 `reason` 并显示。
3. **栈安全意识**：`DeviceProfile` 约 8.5KB，超过 loopTask 的 8KB 栈，代码显式用 `static DeviceProfile blank_profile` + `new` 而不在栈上构造，并留了注释说明原因。这是踩过坑的痕迹。

### 1.4 现状质量验证

```
$ python3 -m unittest discover -s tests -v
test_empty_ai_slots_are_sent_as_clear_commands ... ok
test_sensor_failure_invalidates_last_value ... ok
test_inferred_ai_states_have_no_percentage    ... ok
```

## 2. 产品定位、目标用户与核心痛点

### 2.1 定位

**「桌面上的第二视线」** —— 不打断电脑主工作流的前提下，让用户用余光判断「AI 是否在干活、是否需要我、电脑是否吃紧、环境是否异常」。

明确**不是**：完整聊天界面、任务管理器、环境监测系统、独立语音助手。

### 2.2 目标用户

| 维度 | 假设 | 证据强度 |
|---|---|---|
| 人群 | 在电脑上高频使用 AI 进行编程/写作/研究/长任务的**个人用户** | ⚠️ 假设，PRD 明确标注「需通过用户访谈验证」 |
| 场景 | 多会话并行、长任务后台执行、用户同时处理其他工作 | ⚠️ 假设 |
| 付费意愿 | 未知 | ❌ 无任何调研 |

**这是本项目最大的产品风险**：目标用户是假设，不是结论。整条价值链建立在「用户确实需要余光确认 AI 状态」这个未验证前提上。

### 2.3 核心痛点映射

| 痛点 | 产品的解法 | 实现状态 |
|---|---|---|
| AI 任务跑后台，用户要切窗口查进度 | `ai_list` 页面 + 4 条并行任务 + 状态/耗时/更新时间 | ✅ 已实现 |
| 多会话时不知道哪个卡住了等我 | `_PRIO` 优先级把 `WAIT_INPUT/ASK/ERROR` 排前 | ✅ 已实现 |
| 日程/提醒要离开电脑去查 | `reminder_list` / `today_calendar` / `alarm` 三组件 | ✅ 已实现 |
| 电脑资源紧张但不知是哪一项 | `hw_cards` 四卡 + 负载/空间区分 | ✅ 已实现 |
| 桌温湿度不关心，坏了也不知道 | `environment` 组件 + 采样失效标注 | ✅ 已实现 |
| 数字屏信息不可自定义 | Web 工作台拖排页面/组件/主题 | ✅ 已实现 |

**结论：核心功能矩阵已完整落地，痛点覆盖没有明显遗漏。** 短板不在功能，在「是否真被需要」的验证。

## 3. 设计意图与商业目标

### 3.1 设计意图（明确且一致，值得肯定）

代码注释与文档里反复出现同一条原则：**宁可显示「不知道」，也不显示假的确定**。

| 原则 | 代码体现 |
|---|---|
| 不显示虚构进度 | `prog = 100 if state == DONE else -1`，注释「日志只提供阶段信号，不能推算真实完成百分比」；固件 `-1` 时隐藏进度条 |
| 过期数据不得刷新新鲜度 | `env_seen` 超过 6s 不再上行；`NA` 而非重发旧值 |
| 任务结束必须显式清空 | 每帧无条件 `AI0=`~`AI3=`；注释「避免任务结束后固件继续显示旧任务」 |
| 断线不重放陈旧数据 | `SerialLink._drop()` 排空发送队列，注释「断线前排队的遥测不能在重连后作为新数据发出」 |
| 不把「已发送」当「已生效」 | 只有 `ACK=...,APPLIED` 才置 `applied_version` |
| 固件保持轻 | 「功能变更尽量放客户端；固件只承载渲染能力，长期保持小版本迭代」 |
| 失败保留上一有效配置 | A/B 双槽 + 候选对象先校验 |

这不是常见的「功能堆料」路线，而是把**数据可信度**当作核心资产。PRD §18 列的七条风险里，风险一（AI 来源能力不足）、风险四（错误和过期数据误导）都已在代码层面正面处理。

### 3.2 商业目标：尚未定义

**必须明确指出：项目中不存在任何商业化内容。** 没有成本模型、没有定价、没有目标市场规模、没有竞品分析、没有渠道策略。

`docs/PROTOCOL.md` 和 PRD 都把「个人或团队使用、目标成本」列为**待确认项**，即当前阶段定位是个人自用项目。

| 维度 | 现状 |
|---|---|
| 目标形态 | 个人自用（隐含） |
| 商业模式 | 无 |
| 成本结构 | 未核算（BOM：ESP32-S3 模组 + ST7796 + FT6236 + DHT11 + 电池/电源 + 外壳） |
| 竞品参照 | 无文档。生态位邻近：Pixel Status Board、Ada Display、Tidbyth Gen2、Divoom、以及大量 GitHub 上的 ESP32 桌面屏项目 |

如果目标是**开源自用**，那么「商业目标」应替换为「可持续维护目标」（issue 响应时效、协议向后兼容、文档与代码同步）。如果目标是**产品化**，则需要补 BOM、装配、固件分发渠道（当前无 OTA，用户需手动烧录，这是产品化的硬伤）。

## 5. 用户与市场反馈收集策略

### 5.1 现状：完全为零

`grep -rniE "analytics|feedback|metric|track|event_log"` 在 client 全目录**零命中**。没有遥测、没有本地事件日志、没有 issue 模板、没有用户反馈入口。

这与项目自身的设计原则**自相矛盾**：一个把「可信状态」当作核心资产的产品，自己没有任何使用侧证据。

同时也是**优势**：本地优先、无账号、无云端，符合 PRD 风险六对隐私的要求，收集反馈时不必先解决合规包袱。

### 5.2 分阶段策略（按当前 n=1 状态设计）

#### 阶段 A：先补「工程健康」可观测性（当前唯一该做的事）

**前提认知：n=1 时北极星指标不可测量。** 单用户产品算留存、算 NPS 都没有意义。此阶段目标是把「产品是否在正常工作」变成可观测的，而不是去度量用户价值。

好消息是协议层**已经产生大量信号**，只是没被记录：

| 信号 | 已有来源 | 目前处理 |
|---|---|---|
| 页面浏览 | 固件 `TOUCH=PAGE1..N` / `LAUNCHER_OPEN` / `CONTROL_OPEN` | ❌ 上行解析后被 `_on_uplink` 丢弃（`self.env.update(d)` 顺手吞掉） |
| 配置同步结果 | `ACK/NAK` + reason | ❌ 只用于改状态文案，未落盘 |
| 设备在线状态 | `HB` / `stale:` / `waiting` | ❌ 只有托盘文案 |
| 固件版本 | `FW=0.3.0,...` | ❌ 客户端完全未处理 |
| 慢循环阻塞 | 固件 `SLOW=<us>` | ❌ 未解析（`parse_uplink` 无此 key） |
| AI 状态跃迁 | 客户端 `aiwatch.poll_all()` | ⚠️ 有数据但只发不存 |

**建议动作（成本极低，收益极高）**：

1. `client/workbuddy/telemetry.py`：本地 JSONL 环形日志，写 `~/.workbuddy/usage-YYYY-MM.jsonl`
2. 记录字段（**全部为计数与状态，不含任务名、不含会话内容、不含路径**，严守 PRD 隐私约束）：
   - `ts`、`fw_version`、`client_version`、`platform`
   - `sync_attempt` / `sync_ack` / `sync_nak` + `reason`
   - `device_online` / `device_offline`（含持续时长）
   - `page_view`（page id + 来源：touch）
   - `ai_state_enter`（state 枚举，**不含 task 名/项目名**）
   - `slow_loop`（固件上报的 us 数）
3. Web 设置页加「导出诊断包」按钮：生成一个 zip，含日志 + `config.json` 脱敏副本 + 版本信息，一键复制或下载
4. 补 `parse_uplink` 的 `FW` 与 `SLOW` 解析，把 `firmware` 接进 `_on_uplink`

**为什么先做这个**：它同时解决了 4 个问题 —— 同步无超时可告警、兼容性校验需要真实版本号、固件版本可追溯、反馈时用户能一键给出真实环境。

#### 阶段 B：引入外部用户后（n≈5-20）

| 渠道 | 做法 | 产出 |
|---|---|---|
| GitHub Discussions / Issues | 配 `.github/ISSUE_TEMPLATE/feedback.yml`，强制三问：**你主要用什么 AI 工具** / **屏幕放在哪、距离多远** / **哪个时刻你真的抬头看了屏幕** | 定性痛点排序 |
| 诊断包模板 | 引导用户贴「导出诊断包」，**不含对话正文**，只含状态计数 | 把「感觉不灵」变成 `sync_nak reason=X 出现 12 次` |
| 半结构化访谈 | 每位用户 30 分钟，走 PRD §5 场景 A-F 逐条确认 | 验证目标用户假设是否成立 |
| 5 秒可读性测试 | 真实摆放距离下计时：能否在 3 秒内判断主状态 | 直接验证 PRD §1 的评审目标 |

#### 阶段 C：规模化后（公开分发）

**必须默认关闭、显式 opt-in、且永不采集对话内容**：

- 匿名使用计数（页面配置使用分布、组件类型采用率、AI 来源分布）
- 崩溃与 NAK 率上报
- 明确的「不采集清单」：任务名、项目名、会话内容、错误正文全文、路径、应用清单

这与 PRD §18 风险六一致：**配置文件与遥测都不得包含对话正文与凭证。**

### 5.3 关键洞察：PIR 引脚已预留，正好是「看屏」的唯一客观测量手段

`firmware/src/config.h` 中有：

```c
// ---- 预留（本期不启用，引脚已锁定）----
#define PIN_PIR   7
```

**PIR（人体红外接近传感器）正是测量「用户真的抬头看了屏幕」的唯一低成本客观手段。** 当前所有状态数据都是「设备展示了什么」，没有任何数据回答「用户是否真的用余光消费了这个信息」。

这是把北极星指标从「猜测」变成「可测」的关键杠杆。优先级应高于任何新组件。

## 6. 迭代规划：指标体系与优先级

### 6.1 指标分层（按 n 分阶段，避免用错指标）

**当前（n=1）：只测护栏，不测价值**

| 指标 | 定义 | 目标 | 为什么现在测它 |
|---|---|---|---|
| 同步成功率 | `sync_ack / sync_attempt` | 100% | 配置不生效是唯一的一票否决缺陷 |
| NAK 原因分布 | 按 reason 分组计数 | 无未知 reason | 未知 reason = 未预料的失败模式 |
| 同步中位耗时 | `push_profile` → ACK | < 3s | 体感直接相关 |
| 设备在线时长占比 | 在线秒数 / 进程运行时长 | > 95% | 断线会让所有价值归零 |
| 固件/客户端版本分布 | 版本 → 设备台数 | 100% 已知 | 无版本即无法定位问题 |
| 慢循环次数 | `SLOW` 上报数 | 0 | 渲染卡顿会毁掉「余光可读」 |

**n≈5-20 后：开始测价值**

| 指标 | 定义 | 说明 |
|---|---|---|
| **激活事件** | 首次成功 `ACK` 一份含 `ai_list` 的配置，且设备连续显示 24h | 强预测留存 |
| **时间至首个价值** | 装机 → 首次激活事件的时长 | 反映开箱体验 |
| **周留存** | 激活后第 7 天仍满足「日均 ≥3 次 page_view」 | — |
| **NRU 按 AI 来源分层** | Claude / Codex / ZCode 三类用户分别留存 | 三类工作模式差异大，混算会掩盖真相 |

**公开后：北极星指标**

> **周有效看屏天数** —— 一周内「当天 PIR 触发 ≥N 次且当时屏幕上存在非 IDLE AI 状态」的天数。

这个定义刻意要求 PIR：只有 PIR 触发（真的有人靠近屏幕）叠加当时有值得看的状态，才算一次真实消费。它同时惩罚「装了不用」和「展示了但没人看」。

**必须避免的虚荣指标**：总装机数、累计 page_view、配置保存次数 —— 这些只涨不反映健康。

### 6.2 优先级排序

评分口径：Reach（n=1 时统一按影响面 1-3）× Confidence（证据强度）× 成本倒数。P0=必须先做。

| 序 | 事项 | 类型 | 依据 | 优先级 |
|---|---|---|---|---|
| 1 | **初始化 Git 仓库并首次提交** | 过程 | 无历史 = 一切改动不可回滚；中文字库与协议契约改动风险最高 | **P0** |
| 2 | **配置同步加超时兜底** | 缺陷 | `profile_status` 无超时 → 永久「传输中」，违反 PROTOCOL §5 | **P0** |
| 3 | **本地健康日志 + 诊断包导出** | 可观测性 | 后续所有工作的前提；补齐 6 个已产生但被丢弃的信号 | **P0** |
| 4 | **修复 `NEXT_MILESTONE.md` 状态标注** | 文档 | 失真文档正在误导排期 | **P0** |
| 5 | **真实能力握手：解析 `FW`，按 `schema` 拒绝不兼容推送** | 缺陷 | PROTOCOL §5 明文要求，当前形同虚设 | P1 |
| 6 | **`validate_profile` 补单元测试** | 质量 | 110+ 行规则零覆盖，含 WCAG 对比度与字库检查 | P1 |
| 7 | **修正 `docs/PROTOCOL.md` 中未实现章节（OTA / 二进制分帧）** | 文档 | 协议文档描述了不存在的功能，会误导实现者 | P1 |
| 8 | **PIR 接入，定义并验证北极星指标** | 能力 | 引脚已预留；把「看屏价值」从假设变可测 | P1 |
| 9 | **8 小时 soak test 脚本化** | 质量 | PRD 阶段1 验收要求，当前无证据 | P1 |
| 10 | **Windows 采集补齐** | 覆盖 | `windows.py` 仅 34 行，三平台能力严重不均 | P2 |
| 11 | **`控制中心` → 打开 AI 会话（`OPEN_SESSION`）** | 功能 | PRD REQ-05 缺口；依赖 AI 来源能否定位会话，仍待验证 | P2 |
| 12 | 双端校验规则合并（生成式共享 schema） | 架构 | 消除 `profile.py` / `profile.cpp` 手工同步成本 | P2 |
| 13 | OTA 升级 | 功能 | PROTO §2.1/§4 已设计未实现；产品化硬伤（非自用场景） | P3 |
| 14 | 趋势图 / 导入导出 / 背景图片 | 功能 | PRD P1-P2，资源预算未冻结 | P3 |

**排序原则**（沿用 PRD §16）：可信状态与可靠同步 > 装饰；可读性与异常恢复 > 信息密度；用户配置闭环 > 模板数量。

### 6.3 建议的执行节奏

| 批次 | 内容 | 产出判据 |
|---|---|---|
| 第 1 批（半天） | 事项 1-4 | 仓库有历史；旧固件场景下能超时退出而非卡死；日志文件生成；文档状态行改正 |
| 第 2 批（1-2 天） | 事项 5-7、9 | 向旧固件推送被正确拒绝而非静默失败；校验规则有测试保护；soak test 可一键执行 |
| 第 3 批（1 周） | 事项 8 + 邀请 5 位用户 | 拿到首份真实反馈；北极星指标有第一组实测值 |
| 之后按数据排序 | 12-14 | —— |

### 6.4 三个需要立刻回答的问题

1. **目标用户假设何时验证？** 整条价值链建立在「高频 AI 长任务用户需要余光确认状态」这一未验证前提上。目前 n=1，无法验证。建议在第 3 批之前先做 3-5 个外部用户访谈 —— 成本远低于继续加功能。
2. **开源自用还是产品化？** 决定 OTA、固件分发、BOM 核算是否进入路线。若产品化，「用户需手动烧录固件」是当前最大落地障碍。
3. **PIR 是否值得占用一个引脚和一次功耗预算？** 它是唯一能把北极星指标从主观变客观的硬件投入。但 5mm 传感器有误触与遮挡风险，需实测。
